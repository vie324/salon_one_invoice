# SalonOne — One Platform. One Management.

サロン向けの **契約(申込書)・電子契約・請求書 作成・送付・管理** ＋ **Salon One の開発依頼・エラー進捗報告・進捗管理** アプリケーション。
**Vercel + Supabase** で動くフルスタック構成。**申込と電子契約を1本のURLで完結**させ、**受注管理**で請求開始・口座振替（NSS 日本システム収納）・導入までの抜け漏れを防ぎます。**入金確認機能**も備えます（Stripe も任意で接続可）。担当者の日次オペレーションと、経営者の売上・入金俯瞰の両方に最適化した UI（ディープ・ティール × ゴールドのブランドカラー）です。

> **すぐ試せます。** Supabase を設定しなくても、`npm install && npm run dev` で **デモモード**が起動します（デモでもログインが必要です／ゲストアクセスなし）。
> 業務データは空の状態から始まります（自社情報・料金プラン・契約書テンプレートのみ初期投入。デモモードのデータはインメモリのため再起動でリセットされます）。

## 決済方針（引き落とし × 入金確認）

「原則 引き落とし」にしつつ、初期費用の振込入金なども確認できるよう、**決済プロバイダ非依存**の設計にしています。

- **既定（`manual`）**: 自動与信は行わず、**口座振替は NSS（日本システム収納）**、初期費用などの振込は手動入金確認 ＋ 銀行明細 CSV 照合で消し込みます。NSS への金額登録・振替結果の反映は「NSS引き落とし」画面で行います（口座情報は NSS 側で管理し、このツールには保存しません）。
- **`stripe`**: `PAYMENT_PROVIDER=stripe` と `STRIPE_SECRET_KEY` を設定すると Stripe 参考アダプタが有効になります。
- 独自の収納代行 API を使う場合は、`src/lib/payments/provider.ts` の `PaymentProvider` を実装したアダプタを追加し、`src/lib/payments/index.ts` の分岐に足すだけです。

## クイックスタート（デモモード）

```bash
npm install
npm run dev
# http://localhost:3000 を開く（サンプルデータで全機能が動作）
```

デモモードは Supabase 未設定時に自動で有効化され、インメモリのデータで動作します（データはプロセス内のみ・再起動でリセット）。

**ゲスト（未ログイン）でのアクセスはできません。** デモモードでもログイン画面でデモアカウント（管理者／エンジニア／請求管理者＋開発・修正管理者の兼務／開発・修正管理者）を選んでログインします。ログイン後は右上の「デモ」セレクトでアカウントを切り替えられます。

## 本番セットアップ（Supabase 連携）

1. [Supabase](https://supabase.com) でプロジェクトを作成。
2. `supabase/migrations/*.sql` を順に実行（SQL Editor もしくは Supabase CLI）。
   ```bash
   # Supabase CLI の例
   supabase link --project-ref <your-ref>
   supabase db push        # migrations を適用
   # 初期データ（自社情報・料金プランのみ。テストデータは含まない）
   psql "$SUPABASE_DB_URL" -f supabase/seed.sql
   # 既存DBのテストデータを空にする場合（取り消し不可・実行前に要確認）
   psql "$SUPABASE_DB_URL" -f supabase/cleanup_test_data.sql
   ```
3. `.env.example` を `.env.local` にコピーし、値を設定。
   ```bash
   cp .env.example .env.local
   ```
   最低限:
   ```env
   NEXT_PUBLIC_SUPABASE_URL=...
   NEXT_PUBLIC_SUPABASE_ANON_KEY=...
   SUPABASE_SERVICE_ROLE_KEY=...   # cron/webhook 用（サーバー専用）
   APP_ENCRYPTION_KEY=...          # 申込で預かる ID・パスワードの暗号化鍵（`openssl rand -base64 32`）
   ```
4. 最初のユーザーを Supabase Auth で作成してログイン。管理者がまだ1人もいない場合、**設定画面に「自分を管理者にする」ボタン**が表示されるので押すだけで初期セットアップ完了です（SQL は不要）。以降のアカウント作成・役割変更・パスワード再設定・削除はすべて設定画面から行えます。
5. **設定 → 自社情報（請求書の発行元）** で電話番号・振込先などを入力（管理者のみ）。インボイス登録番号は初期データで投入済みです。ここで入力した内容が請求書・請求書メール・代理店明細にそのまま記載されます。
6. `npm run dev`（または `npm run build && npm start`）。

環境変数の全項目は [`.env.example`](.env.example) を参照してください。

## Stripe で初期費用＋月額を管理する

高額の初期費用（例: 100,000円・単発）と月額（例: 5,000〜30,000円・継続）を **Stripe Checkout 1 回でまとめて登録**し、以降は自動で月額課金します（初期費用は初回請求書に加算）。顧客詳細ページの **「Stripeで課金開始」** から実行します。

### すぐ試す（Stripe キー不要）
「Stripeで課金開始」ダイアログの **「テスト決済をシミュレート」** で、初期費用＋初月の決済成功を再現し、定期契約・請求・入金の管理フローを即座に確認できます（価格帯の検証用）。

### 本番/テストモードの Stripe を接続する
1. `.env.local` を設定:
   ```env
   PAYMENT_PROVIDER=stripe
   STRIPE_SECRET_KEY=sk_test_xxx          # Stripe テストキー
   STRIPE_WEBHOOK_SECRET=whsec_xxx        # 下記 stripe listen が発行
   ```
2. ローカルで Webhook を受ける（[Stripe CLI](https://docs.stripe.com/stripe-cli)）:
   ```bash
   stripe listen --forward-to localhost:3000/api/stripe/webhook
   # 表示された whsec_... を STRIPE_WEBHOOK_SECRET に設定
   ```
3. `npm run dev` → 顧客詳細で「Stripeで課金開始」→ **Stripe Checkout へ進む** →
   テストカード `4242 4242 4242 4242`（有効期限は未来、CVC任意）で決済。
4. Webhook（`checkout.session.completed` / `invoice.paid` ほか）がアプリに同期し、
   初期費用＋初月の入金・定期契約・ダッシュボードが更新されます。

> 本番 Vercel では、Stripe ダッシュボードで Webhook エンドポイント
> `https://<your-app>/api/stripe/webhook` を登録し、その署名シークレットを
> `STRIPE_WEBHOOK_SECRET` に設定してください。

## 申込・契約URL（申込と電子署名を1本で）

メニュー「申込・契約URL」（`/applications`）・「受注管理」・各代理店の画面・「紹介・問い合わせ」の各行から、お客様にお渡しする**申込・契約URL**を発行できます。お客様はログイン不要で、**申込内容の入力から契約内容の確認・電子署名まで**を1本のURLで完了します（以前の「申込を受けてから契約書を別に作って送る」二度手間と送り忘れをなくしました）。

### URLの種類

| 種類 | 使う場面 |
| --- | --- |
| **申込＋契約**（標準） | お客様ごとに渡すURL。プラン・オプションの初期選択・店舗数（指定 or お客様が入力）・個別価格を決めて発行します。 |
| **代理店URL** | 代理店がお客様に渡す常設のURL。「まずは相談したい」（→ 紹介・問い合わせへ）と「このまま申し込む」（→ 申込＋電子署名）を選べます。何件でも受け付け、代理店・営業担当・区分が自動で記録されます。 |
| **紹介から** | 紹介・問い合わせに連絡したあとに送るURL。紹介者・代理店の紐付けと特典を引き継ぎ、お名前・連絡先も入った状態で開きます。 |
| **申込のみ** | 料金がまだ決まっていない場合だけ。届いた申込は受注管理の対応待ちに出るので、「顧客として登録」→ 契約書を作成して送ります。 |

### フロー

1. **URLを発行** — 宛先メモ（例: ○○サロン様）、プラン、オプション、店舗数、必要なら個別価格（初期費用・月額基本料金）、代理店経由なら代理店・営業担当・区分、有効期限を指定。発行画面で料金の見込みが確認できます。「URLをコピー」「案内文ごとコピー」（LINE・メールにそのまま貼れる文面）「QRコード」でお渡しします。メール送信の設定は不要です。
2. **お客様が入力（4ステップ）** — `/apply/<token>` で ①お客様情報（法人名・登記住所・代表者・ご担当者・電話・メール）②プラン・料金（オプション・店舗数を選ぶと初期費用・月額（税込）と支払いの流れを表示）③連携情報（任意。HPB / minimo / EPARK の ID・PASS、LINE連携の希望）④契約書の確認と電子署名（氏名の入力＋同意）。
3. **自動で作られるもの** — 申込・顧客・**締結済みの契約書**（閲覧・同意の日時、IPアドレス、端末情報、内容の SHA-256 ハッシュの証跡つき）を作成し、受注管理に「受注確認」として並びます。お客様へ受付完了メール（契約書の控えのリンクと今後の流れ）、社内へ「受注確認待ち」の通知メールを送ります（メール設定がある場合）。
4. **受注確認・受注確定** — 請求管理者が[受注管理](#受注管理)で内容を確認し「受注を確定する」。契約書第3条のとおり、**契約は当社の承諾（受注確定）で成立**します。

> 送信時にテンプレートが更新されていた場合は送信を止め、最新の契約内容で確認し直していただきます（確認した内容と署名した内容が食い違わないようにするため）。

### 預かった認証情報の取り扱い

お客様の外部サービスの ID・パスワードは、平文で保存しません。

- **保存時に暗号化** — `src/lib/crypto/secrets.ts` で **AES-256-GCM**（`v1:iv:tag:data` 形式）により暗号化して保存します。鍵は環境変数 `APP_ENCRYPTION_KEY`（未設定時は `SUPABASE_SERVICE_ROLE_KEY`）から導出し、**DB には保存しません**。
- **既定はマスク表示** — 申込詳細では `lu••••••` のようにマスクされ、**平文はページの HTML にも含まれません**。連携作業を行う担当者が「表示する」を押したときだけサーバー側で復号して返します。
- **顧客の備考には残さない** — 「顧客として登録」で作成される顧客メモには、代表者と希望連携のみを引き継ぎます（ID・パスワードは暗号化された申込レコードにのみ保持）。
- **鍵の変更に注意** — 鍵をローテーションすると、それ以前に保存した認証情報は復号できなくなります（画面には「復号できません」と表示されるため、お客様に再入力を依頼してください）。

> 申込フォームは認証ゲートの対象外（公開ルート）で、アクセス制御は**暗号乱数トークン（48桁）＋受付停止＋有効期限**で行います。フォームからの読み書きはサーバー側のサービスロール経由のみで、トークンを知っていても DB を直接読むことはできません。
> 申込の閲覧・URL 発行は**請求管理の権限**（管理者・請求管理者）が必要です。

既存のお客様からのご紹介を受け付け、特典を請求まで自動でつなげる仕組みです（メニュー「紹介・問い合わせ」／`/referrals`）。代理店URLの「まずは相談したい」から届いた問い合わせも同じ一覧に「代理店経由」として並びます。

### 特典の設計

| 対象 | 特典 |
| --- | --- |
| **紹介した側** | ご紹介いただいた方の**初期費用の25%**をお支払い |
| **紹介された側** | **初月の端数日数（日割り分）＋2ヶ月無料** |

率と月数は [`src/lib/domain/constants.ts`](src/lib/domain/constants.ts) の `REFERRAL_REWARD_RATE` / `REFERRAL_FREE_MONTHS` で変更できます。

### フォーム（お客様が入力する）

- **常設URL: `https://＜サイト＞/refer`** — ログイン不要で誰でも開けます。**このURLをそのまま配れます**（紹介・問い合わせの画面からコピーできます）。
- **紹介者ごとのURL: `https://＜サイト＞/refer/＜トークン＞`** — 紹介・問い合わせの画面から「紹介者を指定したURLを発行」で作ります。開くと「どなたのご紹介ですか？」が**その方の名前で固定表示**され、入力ミスなく紹介元をたどれます。受付停止・有効期限は申込URLと同じ扱いです。
- 入力項目: **どなたのご紹介か** / 店舗名・法人名（任意）/ お名前 / 電話番号 / メールアドレス / **連絡してほしい方法（電話・メール・SMS・LINE）** / **連絡希望日** / **希望の時間帯**（いつでも・午前中・12〜15時・15〜18時・18時以降）/ ご相談内容。
  - 必須の連絡先は**選ばれた連絡方法にあわせて変わります**（メール希望ならメールアドレス、それ以外なら電話番号）。
  - フォームの先頭に特典（初月の端数日数＋2ヶ月無料）を明記しています。

### 管理（紹介・問い合わせの画面）

- **連絡すべき順に並びます**（未対応→連絡済、連絡希望日が早い順、同じ日なら希望の時間帯が早い順）。**連絡希望日を過ぎたものは赤く表示**され、上部に件数が出ます。
- 「どなたのご紹介か」は、**同じ名前の顧客が1件だけ見つかれば自動で紐付き**ます。違っていればプルダウンで選び直せます（紐付けが謝礼のお支払い先になります）。
- 連絡して申込の意向が固まったら、その行の「**申込・契約URLを発行**」で送ります。お客様が申し込むと、紹介者との関係（`referredByCustomerId`）・代理店・特典が自動で引き継がれます（URLを使わずに「顧客として登録」することもできます）。

### 既存機能との連携

- **受注確定 → 請求**: 紹介から申し込んだお客様の[受注を確定](#受注管理)すると、特典が自動で適用されます。
  - 初回請求の**初月日割りが0円**になります（`月額利用料 初月日割り（9月3日〜月末・28日分）※ご紹介特典により無料` のように、**何が無料になったか分かる明細**として残します）。
  - 定期請求の**初回請求日を2ヶ月先送り**します（例: 9/3 開始なら通常は10/27→**12/27**。9月の日割り・10月・11月が無料）。
  - **紹介した側へのお支払い（初期費用の25%）が確定**し、紹介・問い合わせの画面に「お支払い待ち」として出ます。お支払いしたら「お支払い済にする」で記録します。
  - 契約書の証跡にも `ご紹介特典により初月日割り 28,000円を無料 / ご紹介者へのお支払い 50,000円(初期費用の25%)を計上 / 2026/09/03 〜 2026/11/30 は無料` のように残ります。
- **顧客**: 紹介された側の顧客メモに、紹介者・特典・連絡希望が記録されます。
- **最近の動き**: フォームからの受付がダッシュボードの活動履歴に流れます。

## 契約書・電子契約

通常の契約は[申込・契約URL](#申込契約url申込と電子署名を1本で)でお客様が申込と同時に署名します。条文を変える契約や、アクセスコードで本人確認を強めたい場合は、「契約書」メニューから **作成 → 編集 → 電子署名依頼 → 締結 → 受注確定** までを個別に行えます。

### フロー

1. **テンプレートから作成** — 標準の「SalonOne サービス利用契約書（全23条）」テンプレートを同梱。契約作成時に内容がコピーされるため、顧客ごとに料金表・条文を自由に編集できます（テンプレート変更は既存契約に影響しません）。
2. **プラン連携** — プランを選ぶと申込条件（初期費用・月額・オプション・店舗数）が自動反映され、「プランから料金表を生成」で契約書の別表を自動作成できます。
3. **署名依頼** — 渡し方を選べます。**送付時に契約内容の SHA-256 ハッシュを固定化**し、以降の内容変更は DB トリガーでも拒否されます。
   - **メールで送る** — 契約者のメールアドレスへ専用リンクを送付します。
   - **リンクを発行して自分で渡す（メールを送りません）** — 署名リンクとQRコードを画面に表示。LINE・SMS・対面（お客様のスマホで読み取り）でお渡しできます。メール送信が未設定の環境ではこちらが既定になります。
4. **契約者の署名** — 契約者はリンクから内容を確認し、氏名の記入＋同意チェックで電子署名。締結証跡（閲覧・同意の日時、IPアドレス、端末情報）が記録され、双方に締結完了メールが届きます。
5. **締結後** — 受注管理の「受注を確定する」（契約書の画面の「受注を確定（請求を開始）」でも可）で定期契約と初期費用請求書を自動作成。締結証明書付きのPDF出力が可能です。

### 電子署名の法的リスク低減のための設計

本機能は **事業者署名型（立会人型）電子署名** の考え方に基づき、以下を実装しています。

- **本人性の担保（2要素）**: 契約者本人へ渡す専用リンク（暗号乱数トークン・有効期限付き）に加えて、**6桁アクセスコード**（リンクやメールに記載せず、電話等の別経路で伝達）を推奨設定。誤入力の試行回数制限つき。リンク発行（メールなし）で渡す場合も、リンクの経路とコードの経路を分けることで2要素になります。
- **非改変性の担保**: 送付時に契約内容の正規化 JSON を SHA-256 でハッシュ化して固定。**署名時にハッシュを再計算・照合**し、送付後の内容変更は DB トリガー（`contracts_freeze_content`）でサービスロールを含む全経路で拒否。
- **証跡の保全**: 作成・送付・閲覧・コード検証・署名・辞退・取消の全イベントを **追記専用の監査ログ**（UPDATE/DELETE を DB トリガーで禁止）に IP・UA・時刻付きで記録。締結証明書として書面化・PDF保存可能。
- **電子帳簿保存法への配慮**: 締結済み契約は削除不可（取消は状態として記録）、契約一覧は取引先・日付・金額で検索可能。訂正削除の防止措置を DB レベルで実装。

> **注意（法務向け）**: 本実装はいわゆる認定タイムスタンプ（TSA）や当事者型電子証明書は使用しません。多くの SaaS 利用契約はこの方式（立会人型）で実務上広く運用されていますが、
> 訴訟リスクの高い高額契約等では、締結証明書PDFの長期保管、アクセスコードの別経路伝達の徹底、必要に応じた外部電子契約サービスの併用をご検討ください。
> 運用ルール（誰が送付できるか、コードの伝達方法等）を社内規程として定めることを推奨します。

### 紙の契約書にも対応

書面で締結した場合は「書面締結を登録」から締結記録（署名者・締結日・原本保管場所）を登録でき、電子・紙どちらの締結経路でも契約管理を一元化できます。

## 受注管理

メニュー「受注管理」（`/orders`）。申込から運用開始までを、案件（お客様1件）ごとに抜け漏れなく進めるための画面です。

| ステージ | 状態 | 主な担当 |
| --- | --- | --- |
| **申込・契約** | URLを渡し、お客様の申込・電子署名を待っている | お客様（営業・代理店がフォロー） |
| **受注確認** | 締結済み。内容を確認して「受注を確定する」を押す | 請求管理者 |
| **導入準備** | 初回請求・入金／口座振替（NSS）／初期設定・導入 の3つを並行で進める | 請求管理者・導入担当（代理店） |
| **運用中** | すべて完了。毎月の請求・NSS引き落としへ | — |

- **ステージは自動**: 締結・初回請求・入金・NSS登録などの実データと、導入のチェック（初期設定・納品など）から判定します。手で動かす必要はなく、ずれることもありません。
- **対応待ち**: 「届いた申込の確認（申込のみURL）」「契約書の作成・送付」「受注確認待ち」「初回請求書の送付」「入金確認」「依頼書の郵送・回収・NSS登録（不備の再提出を含む）」「初期設定・納品」のように、**やることごとに担当別でまとめて**表示します。遅れ（入金期限の超過・依頼書の回収が郵送から14日超など）は赤く表示し、ホームの「いま急ぐこと」にも出ます。
- **受注を確定する**: 利用開始日を選ぶと、初回請求書（初期費用＋初月日割り・銀行振込・期限14日）、毎月の定期請求（**店舗数・個別価格も契約書どおり**）、支払方法の口座振替（NSS）への切替、紹介特典・代理店報酬の計上をまとめて行います。確定画面で金額を確認でき、初回請求書をそのままメール送付することもできます。
- **口座振替（NSS）の記録**: 案件ページで「郵送した」「回収した」「NSSへ登録した」「登録完了（振替開始月を記録）」「不備あり」「再提出した」を記録します。
- **休止・見送り**: 理由を残して案件を閉じられます（再開も可能）。旧「顧客ステータス」（`/pipeline`）を開くと受注管理へ移動します。

## 代理店

メニュー「代理店」（`/agencies`）。

| 区分 | 代理店が担当する範囲 | 報酬 |
| --- | --- | --- |
| **取次型** | お客様のご紹介（取次）まで。商談・お申込み手続き・初期設定は当社 | **初期費用（税抜）の50%** |
| **営業・初期設定型** | 営業（商談〜お申込み手続き）と初期設定まで | **初期費用（税抜）の100%** |

伴走型（導入後の運用支援まで担当）は今後追加予定です。率は [`src/lib/domain/constants.ts`](src/lib/domain/constants.ts) の `AGENCY_DEAL_TYPES` で管理しています。

1. **代理店を登録** — 区分（既定）を選んで登録し、営業マンを追加します。案件ごとに区分を変えたいときは顧客の「代理店区分（この顧客）」で上書きできます。
2. **代理店URLを発行** — 代理店の画面の「URLを発行」。営業担当ごとに分けると担当別の実績が出ます。「案内文ごとコピー」で使い方つきの文面を代理店へ送れます。
3. **お客様が相談 or 申込** — 「まずは相談したい」は紹介・問い合わせに代理店経由として届き、「このまま申し込む」は申込＋電子署名まで完了して受注管理に並びます。
4. **報酬の計上** — 受注確定で初期費用 × 率を計上（同じ請求に二重計上しません）。**お客様の初期費用の入金を確認した月**の支払明細に入ります（それまでは「初期費用の入金待ち」）。計上時の区分・率で固定されるため、後から代理店の区分を変えても計上済みの報酬は変わりません。
5. **毎月の支払い** — 月を選んで明細をメール送付・印刷/PDF。支払ったら「支払済みにする」。未払いは月をまたいで残ります。

## NSS 口座振替（日本システム収納）

口座振替は NSS のみを利用する前提で、このツールの口座振替機能を整理しました。**口座情報（銀行・口座番号・名義）はこのツールに保存しません**（旧運用で保存していたものは顧客・案件ページの「口座情報を消去」で削除できます）。

| 項目 | NSS で行うこと | このツールで行うこと |
| --- | --- | --- |
| 口座情報 | 登録・保管 | 持たない |
| 登録の進み具合 | — | 依頼書の郵送 → 回収 → NSSへ登録 → 登録完了・振替開始月 を記録し、遅れを知らせる |
| 毎月の金額 | 収納リンクへ確定金額を登録 | 引き落とせる／引き落とせない請求の振り分け、登録用の一覧（CSV・確認用） |
| 引き落とし | 実行（毎月27日予定） | — |
| 結果 | 振替結果を提供 | 請求へ反映（済＝入金済／不可＝引落失敗・要フォロー） |

毎月の流れ（メニュー「NSS引き落とし」／`/direct-debit`）:

1. 請求書の自動作成・送付 → **確認期間（発行から7日）**。修正があれば請求書を訂正します。
2. その月の対象を確認。**NSS の登録が終わっていない（振替開始月より前を含む）請求は「引き落とせない請求」**に出るので、「振込に切り替える」で請求書の案内を振込に変えます。
3. 「NSS登録用の一覧を作る」→ 一覧（CSV）を見ながら NSS へ金額を登録 →「NSSへ登録した」。
4. 引き落とし日のあと、NSS の振替結果を見ながら「結果を反映する」（不可は理由を選ぶ）。不可は振込に切り替えて請求書・督促を送ります。

> 以前の「登録状態だけで成功／失敗を自動判定する処理」と「汎用の収納代行向けCSV」は廃止しました。結果は必ず NSS の実際の振替結果を反映します。

## 定期請求の自動生成・自動送付（Cron）

`/api/cron/generate-invoices` が、次回請求日（`next_billing_date` ＝ 引き落とし日・支払期限）がその月のうちに来る稼働中の定期契約について、**月初（発行日＝1日）に請求書を生成**します（`billing_period` 単位で二重生成を防止）。引き落とし日（27日）の前に、お客様の確認期間（約7日）と NSS への金額登録の時間を確保するためです。生成した請求書は、顧客にメールアドレスが登録されていれば**自動でメール送付**されます（`INVOICE_AUTO_EMAIL=false` で無効化）。

- **Vercel Cron**: [`vercel.json`](vercel.json) に日次スケジュールを定義済み。Vercel が `Authorization` を自動付与します。
- 手動実行:
  ```bash
  curl -H "Authorization: Bearer $CRON_SECRET" https://<your-app>/api/cron/generate-invoices
  ```
- アプリの「定期請求」画面の **「定期請求を今すぐ生成」** ボタンからも実行できます。

## メール送付

契約書の署名依頼・締結完了通知、請求書、代理店の支払明細はすべて同じメール設定を使います。

- 既定（未設定）: **実送信せずプレビュー**（サーバーログ出力のみ）。画面には「メールは送信していません（プレビューのみ）」と表示されます。
- **実送信にする**: 次のどちらかを設定すると、自動的に実送信モードになります。
  - **SMTP（推奨）** — `MAIL_HOST` / `MAIL_PORT` / `MAIL_ENCRYPTION` / `MAIL_FROM_ADDRESS`。Google Workspace の SMTP リレー（`smtp-relay.gmail.com:587`）や Gmail の SMTP 送信に対応します。自社ドメインのアドレス（例: `noreply@salonone.net`）から送れます。
    - **認証方法は2通り**で、リレー側の設定に合わせます。
      - **SMTP 認証** — `MAIL_USERNAME` + `MAIL_PASSWORD`（Google の**アプリ パスワード16桁**。通常のログインパスワードは不可）。**Vercel から送る場合はこちらが必須**です。
      - **送信元IPの許可のみ** — `MAIL_AUTH=none` を設定し、認証情報は使いません。**固定グローバルIPのサーバーからのみ**送れます（Vercel はサーバーレスで送信元IPが変わるため不可）。
    - 疎通確認は `npm run mail:test`（送らずに接続だけ確認。許可リストに登録する送信元IPも表示）、`npm run mail:test you@example.jp`（1通送る）、または 設定 → メール送信 の「接続確認 / テスト送信」。
  - **Resend** — `RESEND_API_KEY` と `EMAIL_FROM`。`EMAIL_FROM` は Resend で認証済みドメインのアドレスにしてください。
  - メール内のリンク（署名URL・請求書URL）を正しくするため、`NEXT_PUBLIC_APP_URL` に公開URLを設定してください。
  - 意図的にプレビューへ戻す場合のみ `EMAIL_PROVIDER=console` を設定します。
- **確認方法**: アプリの **設定 → メール送信** で現在のモード・送信元・不足している設定を確認でき、全体管理者は**テスト送信**で実際に届くか試せます（お客様には送信されません）。

## アカウントの役割（ロール）

**1つのアカウントに複数の役割を兼務させられます**（例: 請求管理者 ＋ 開発・修正管理者）。

| ロール | 表示名 | できること |
| --- | --- | --- |
| `admin` | 管理者 | 全機能 ＋ アカウント管理。**要望の実行を承認する「承認者」**になります。 |
| `engineer` | エンジニア | 開発進捗の対応担当。完了日・開発対応内容を入力します。 |
| `billing` | 請求管理者 | 請求書・顧客・契約・入金などの請求業務。 |
| `dev_manager` | 開発・修正管理者 | 不具合報告・要望の起票と進捗管理。請求管理者との兼務が可能。 |
| `owner` / `staff` / `dev` | 旧種別（後方互換） | `owner`→管理者、`staff`→請求管理者、`dev`→エンジニアとして動作。役割変更で新しい役割へ移行します。 |

- 役割は `profiles.roles`（配列）で管理します（`profiles.role` は主ロールとして後方互換のため保持）。設定画面（管理者のみ）から**アカウントの作成・役割変更（複数選択）・名前変更・パスワード再設定・削除**ができます。
- **兼務の重複チェック**: 設定画面のアカウント管理に、複数の役割を持つアカウントの一覧と、**同じメールアドレスで二重登録されているアカウントの警告**が表示されます。
- **初期セットアップ**: 管理者が1人もいない場合、設定画面に「自分を管理者にする」ボタンが表示されます（SQL 不要でアプリ内完結）。
- アカウントを削除しても、過去の開発依頼・実行判定の履歴は名前付きで残ります（`requester_name` を保持）。
- アカウントの作成・パスワード再設定・削除には `SUPABASE_SERVICE_ROLE_KEY`（サービスロール）が必要です。
- デモモードではログイン画面でデモアカウントを選んでログインし、ログイン後は右上の「デモ」セレクトで切り替えられます。

### ログイン必須（ゲストアクセスなし）

- **URL を開いた時点でログイン状態を確認**します。未ログインで `/dashboard` などを開くと `/login?redirect=...` へ送られ、ログイン後に元のページへ戻ります。
- 匿名（ゲスト）でアプリを閲覧することはできません。デモモードでもログインが必要です。
- 認証ゲートは [`src/middleware.ts`](src/middleware.ts) と、各ページの `requireUser()`（[`src/lib/auth.ts`](src/lib/auth.ts)）の二段構えです。
  - ⚠️ middleware は `src/` 配下に置く必要があります（`src/app` を使う構成でプロジェクト直下に置くと Next.js が読み込まず、認証ゲートが働きません）。ビルド出力に `ƒ Middleware` の行が出ることで確認できます。
- ログイン不要で開けるのは、ログイン画面・決済の戻り先（`/billing/*`）・トークンで保護された電子契約の署名ページ（`/sign/*`）・**申込フォーム（`/apply/*`）**のみです。
- サインアウトは設定画面から行えます（デモモードでも利用可）。

## 削除・復元（ゴミ箱）

テストで投入したデータを、記録を残したまま片付けられます。メニュー「ゴミ箱」。

- **対象**: 請求書 / 顧客 / 入金 / 定期契約 / 銀行明細 / NSS引き落としの一覧
- **削除してもデータは消えません** — `deleted_at` を立てて一覧・集計・ダッシュボードから外すだけです。定期請求の自動生成対象からも外れます。
- **復元**: ゴミ箱の「復元」でいつでも元に戻せます。
- **操作ログ**: 誰が・いつ・何を・どんな理由で削除／復元したかを `data_deletions` に記録します。**追記専用**で、更新・削除は DB トリガーで拒否されます。
- 削除時には理由の入力欄が出ます（例:「テストで登録したデータのため」）。

> 締結済みの契約書は電子帳簿保存法の観点から削除対象に含めていません（取消は状態として記録します）。

## 開発進捗（開発依頼・エラー進捗報告）

スプレッドシートで運用していた「開発対応表」をそのままシステム化したものです（メニュー「開発進捗」）。

- **記載日・依頼者はアカウントから自動記録** — 入力工数を削減。
- 依頼側の入力項目: 課題名 / 詳細 / 分類（不具合・要望）/ 優先度（高・中・低）。
- エンジニア入力: ステータス（未対応・対応中・追加ヒアリング・対応完了）/ 対応完了日 / 開発対応内容。
- **完了希望日・完了予定日は扱いません**。日付を出し合って擦り合わせる運用は負担が大きかったため廃止し、**急ぎ具合は「分類・優先度・並び順」で表す**方針にしています。
- **手動の並び替え** — 「並び順: 手動（ドラッグで入替）」に切り替えると、行をつかんで上下にドラッグして**対応の順番を入れ替えられます**（矢印ボタンでも移動可）。並び順はそのまま保存され、全員に共有されます。
- **緊急度順に表示**: 一覧は **不具合 → 要望**、**優先度 高 → 中 → 低**、**古い依頼ほど上**の順で並びます。長期滞留（7日以上）の依頼は経過日数を赤く表示します。
- **完了した依頼は既定で非表示**: 開いた直後は「未完了」タブです。完了した依頼は消えず、「完了」「すべて」タブから確認できます。
- **追加ヒアリングのやり取り（返信の追記と共有）**: ステータスを「追加ヒアリング」にすると、詳細画面に**やり取りのスレッド**が出ます。
  - 依頼者は**確認事項への返信を追記**でき、追記すると**エンジニアへ通知**が届きます（エンジニアからの追いヒアリングは依頼者へ届きます）。
  - 各返信には**「エンジニアへ通知済み」＋通知した相手の氏名**がバッジで付き、**誰に共有できたか**がその場で分かります。
  - 一覧・詳細には状況バッジが出ます。**「ヒアリング返信あり」＝エンジニアが確認する番**（返信が届いた依頼は緊急扱いで強調）、**「ヒアリング返信待ち」＝依頼者が答える番**。
  - エンジニアがステータスを「対応中」などに戻すと、これらのバッジは自動で消えます。
- **役割ごとの督促バー**: 画面上部に、いま急ぐことだけを出します。
  - 承認者（管理者）→ 「あなたの承諾待ちが N件あります」
  - それ以外 → 「承諾待ちの要望が N件（◯◯さん・△△さん の確認待ち）」
  - 依頼者本人 → 「あなたへの追加ヒアリングが N件あります」
  - エンジニア → 「追加ヒアリングに返信が N件届いています」
- **実行有無（管理者のみ編集可）**: 要望は**承認者（管理者ロール）全員の承諾**で「実行」、1名でも停止で「実行なし」。**未承諾の承認者は名前付きで一覧・詳細に表示**され、本人が見ると「あなたの承諾待ちです」と強調されます。管理者は「実行有無を直接変更」から承諾を待たずに確定もできます（誰がいつ設定したかを記録し、「承諾状況からの自動判定に戻す」で解除）。
- **通知**: 対応完了で依頼者・管理者に通知（未読のあいだトップにバナー表示）。新規依頼・追加ヒアリング・**ヒアリング返信**・実行判定も通知されます。
- **スクリーンショット添付**: 依頼フォーム・詳細画面へ**ドラッグ&ドロップ**、ファイル選択、または画面上で `Ctrl+V`（⌘+V）貼り付け。画像は自動で縮小してアップロードされます（本番は Supabase Storage・非公開バケット＋署名付きURL）。
- **画像への書き込み**: 添付画像にペン・矢印・枠・テキストで注釈を入れ、別画像として保存できます（元画像は残ります）。
- **急ぎの項目をワンタップで共有（短縮URL）**: 依頼の詳細・一覧カードにある「共有」から、端末の共有シート（LINE・メール・Slack・AirDrop など）へそのまま渡せます。
  - 共有されるのは `https://＜サイト＞/d/12` のような**依頼番号だけの短いURL**です（UUID の長いURLを貼らなくてよく、口頭でも伝えられます）。開くと該当の依頼へ転送されます。
  - 共有シートが無い環境（PCブラウザなど）では、**URLコピー / 本文つきコピー / QRコード / 別タブで開く**を選べます。本文には「#12 課題名（不具合・優先度高・対応中）」のような要約が入り、相手はリンクを開く前に急ぎ具合が分かります。
  - **まとめて共有**: 一覧の「選択して共有」で急ぎの依頼を複数タップして選ぶと、番号つきの一覧＋短縮URLを **1通のメッセージ**にして送れます。
  - 未ログインの相手が短縮URLを開いた場合はログイン画面を経由し、**ログイン後にその依頼へ戻ります**（絞り込み条件つきのURLも保持されます）。
- **AI画像モック生成**: 詳細画面の「AIモック生成」で、理想のUIを文章で伝えるとワイヤーフレーム画像を生成して添付できます。トークン消費を抑えるため **HTMLではなく軽量なレイアウト定義（JSON）だけを Claude に生成させ、画像化はブラウザ内で行います**（1回あたり数百〜千数百トークン程度）。利用には `ANTHROPIC_API_KEY` の設定が必要です（`ANTHROPIC_MODEL` でモデル変更可・既定 `claude-opus-5`。未設定時はデモ用サンプルでフローを確認できます）。

## 進捗ホーム（売上と開発を1画面で）

「売上はどこまで来ているか」「開発はどこで止まっているか」を、**アプリを開いた直後の1画面**で掴めるようにした画面です（メニュー「進捗ホーム」／トップ `/` とホーム画面に追加した PWA の起動先もここ）。

- **いま急ぐこと** — 売上側と開発側の要対応を**1つのリストに混ぜて**、赤（止まっている）→ 黄（急ぐ）→ 青（手番が来ている）の順に並べます。タップでその画面へ直行します。
  - 請求: 期限超過の請求（未収額つき）／未消込の入金明細／下書きのままの請求書
  - 開発: 急ぎの開発依頼（うち7日以上 滞留している件数）／あなたへの追加ヒアリング／ヒアリングに届いた返信（エンジニア）／あなたの承諾待ちの要望（管理者）
  - 何も無ければ「いま急ぎの対応はありません」とだけ出ます。
- **売上の進捗** — 今月の請求・入金（前月比・回収率）・未収金・MRR の4指標、**回収率バー**（入金 / 請求）、直近6ヶ月の推移グラフ。詳細はダッシュボードへ。
- **開発の進捗** — 未完了・対応中・今月の完了（今月の起票つき）・7日以上 滞留の4指標、**未完了の内訳バー**（未対応 / 対応中 / 追加ヒアリング＝どこで止まっているか）、**急ぎの依頼 上位3件**（急ぐ理由を「返信あり」「N日 経過」「承諾待ち」のバッジで表示）。
- **役割で出し分け** — 請求権限が無いアカウントには売上セクションを表示しないだけでなく、**売上データの取得自体を行いません**。開発権限が無いアカウントも同様です。
## 開発スケジュール（中長期ロードマップ）

週1回の開発MTGで「**今週なにを進めるか**」を共有するための表です（メニュー「開発スケジュール」／`/dev/schedule`）。
スプレッドシートで管理していた中長期スケジュールを、開発進捗と連動する形でシステム化しています。

### 表の作り

- **1行＝1つの機能**（スプレッドシートの1行と同じ）。カテゴリ / 機能名 / 優先度（★1〜5）/ 対応する月 / 目安日 / メモを持ちます。
- **横軸は月**。当月から先の月が列になり、登録した項目のある月まで自動で伸びます。**当月の列は色付き＋「今月」**で強調されます。
- セルの印はスプレッドシートと同じ意味です。**★＝日程が確定** / **☆＝未確定** / **チェック＝完了**。見送りにした機能は取り消し線で静かに残ります。凡例は表の見出しに常時表示しています。
- **見やすさ**: カテゴリは領域ごとに色分け、優先度は★＋数字、確定した日程は色付きのバッジで表示します。横スクロールしても**「カテゴリ」「機能」の2列は左に固定**されるので、どの行を見ているか見失いません（スマホでも同じです）。
- **並べ替え**: 管理者は**行をつかんで上下にドラッグ**すると順番を入れ替えられます（タッチ操作用に**↑↓ボタン**も併設）。並び順は保存され、全員に共有されます。

### 開発進捗との連動

- 1つの機能に**開発進捗の依頼を複数ぶら下げられます**。連動先は**いま挙がっている不具合・要望の一覧から直接選ぶ**方式です（番号を打ち込む必要はありません）。
  - **「すべて / 不具合 / 要望」で絞り込み**、課題名や番号で**検索**して、チェックを入れるだけで連動します。
  - 選んだ依頼は入力欄の上に**チップで一覧表示**され、×でそのまま外せます。
  - 既定では**未完了の依頼だけ**が候補に出ます（完了・実行なしのものも、チェック1つで候補に加えられます）。
- 連動した依頼の**ステータスは常に最新**が出ます（依頼側で「対応完了」にすれば、スケジュール表の進捗もその場で進みます）。
- **依頼の一覧は畳んであり、既定では「開発進捗 6件」という件数と進捗バーだけ**を表示します。エンジニアが最初に見るのは「今週は機能◯件」という粒度で、依頼の件数が並んで圧を与えないようにしています。開きたいときだけ展開でき、各依頼は `#143` から詳細へ飛べます。

### 今週の共有

- **今週に進める分**が画面のいちばん上に出ます（目安日がその週に入っている機能、または状況を「今週対応」にした機能）。
- **見出しの「◯/◯週」は自動で更新されます**。ページは常にサーバーで描画し、開いた日時から「月曜はじまりの今週」を計算するため、週をまたぐと表示中の週と対象の機能が自動的に切り替わります（手動の操作は不要です）。
- 先週までの予定で終わっていないものは「**先週までの予定で、まだ終わっていないもの**」として、督促ではなく**今週に載せ直す候補**として静かに並びます。
- 「**今週分をコピー**」で、`・勤怠管理（9/7） #143 #156` のような**機能ごとに番号をまとめた文面**をコピーできます。開発MTGやチャットへそのまま貼れます。

### 閲覧できるメンバー（設定画面のチェックボックス）

- 設定画面の「**開発スケジュールを見られるメンバー（全体管理者のみ）**」で、メンバーごとにチェックを付け外しします。
- スケジュール表は**既定では表示されません**。チェックを入れた人だけが開けます（メニューにも出ません。URLを直接開いても開発進捗へ戻されます）。
- **管理者は常に閲覧・編集できます**（自分でチェックを外して締め出される事故を防ぐため、チェックの対象外です）。
- 初期状態では「**酒井**」「**若林**」の2名にチェックが入ります（移行 `0019` が `profiles.schedule_visible` を立てます）。以降は設定画面で増減できます。
- 表の**編集（機能の追加・変更・削除・並べ替え）は管理者のみ**です。閲覧を許可されたメンバーには編集ボタンもドラッグ操作も出ません。

## スマートフォン対応（モバイル UI / UX）

現場・移動中でもそのまま使えるよう、スマートフォン表示を前提に作っています。

- **アプリのように使える**: `viewport` / テーマカラー / Web アプリマニフェストを設定済み。ブラウザの「ホーム画面に追加」でアドレスバーのないフルスクリーンのアプリとして起動できます（iOS 用アイコンも生成）。ノッチ・ホームバーのセーフエリアにも対応。
- **下部タブバー**: よく使う画面（**ホーム＝進捗ホーム**、役割に応じて 受注管理 / 請求書 / 開発進捗 / 不具合 / 設定 など）へ 1 タップで移動。5つ目の「メニュー」で全メニューのドロワーを開けます。ドロワーは左へスワイプ、または背景タップで閉じられます。
- **ヘッダーに現在地**: サイドバーが見えないスマホでも、いまどの画面かがヘッダーに出ます。
- **一覧は「1件 = 1カード」**: 横スクロールしていた表を、スマホでは項目名つきのカードに積み替えて表示します（見出しの文言を各項目のラベルとして自動で引き継ぐため、すべての一覧に適用されます）。開発進捗の一覧は、分類・優先度・ステータス・対応完了日まで1画面で読める専用カードです。
- **受注管理はスマホでも1列**: 対応待ち・案件一覧はカードで縦に並び、案件ページの「次にやること」のボタンからそのまま手続きを記録できます。
- **入力しやすさ**: 入力欄は 16px / 高さ 44px 以上（iOS がフォーカス時に画面を勝手に拡大するのを防止）。電話番号・郵便番号・口座番号などは端末のキーボードを最適化し、氏名・住所・メールは自動入力に対応。
- **ダイアログはボトムシート**: 画面下から出て、上部のハンドルを下へスワイプすると閉じられます。背面のページはスクロールしません。
- **不具合報告がその場でできる**: 開発依頼のスクリーンショットは、写真の選択に加えて**カメラ撮影**からも添付でき、画像への書き込み（ペン・矢印・枠・テキスト）は指で操作できます。
- **お客様向けページ**: 申込・契約フォームは「次へ／署名」ボタンを画面下に固定し、長い入力でもすぐ進めます。契約書・請求書のドキュメント表示もスマホ幅に最適化しています。
